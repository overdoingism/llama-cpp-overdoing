# Benchmark 2026-10-18

Patch set: `0001`-`0005` as on [2026-10-15](2026-10-15.md), plus the new `0006-097-mmvk-v2`, on rdna-boosts `v12-097cf33d9-r59`.
Written with Claude (AI).  R9700, Linux, unless noted.

## What 0006 does

Decode and speculative verification run the matmuls with 1 to 8 tokens.  For Q4_K / Q5_K / Q6_K weights, `0006` replaces the
stock kernel there with one where a lane owns one 32-value sub-block, loads the q8_1 activations of every token once, and runs
several weight rows against them; with `GGML_CUDA_MMVK=2` the matmuls that read the same input (gate + up, q + k + v, DeltaNet
qkv + z) also go out as one launch, mixed weight types allowed.

- The integer dot products and scales are the stock kernel's; only the order of the float sums differs, so the output is not
  bit-identical to the stock kernel.  Decode and verification use the same per-output order, so a run with a draft gives
  exactly the tokens of a run without one.
- `1` / `2` are on only when llama-server verifies drafts (draft model, MTP or an n-gram type): llama-server tells the backends
  before it loads the models, and the log prints `mmvk on (...)` or `mmvk off (...)`.  Without drafts every step is a one-token
  decode, where the stock kernel is 1-1.6% faster on the 27B models (below).  `3` / `4` force it on.
- Off unless `GGML_CUDA_MMVK` is set.  Weight types it does not take (Q8_0, IQ4_XS, MXFP4, ...) are not touched.

## Standard benchmark

Same setup as [2026-10-07](2026-10-07.md) (32K-token prompt, 512 greedy tokens, DFlash2 draft 5, q8_0 KV, 3 rounds); "all on" as
on 2026-10-15.  Both configurations in the same session (Q5: on, +0006, +0006, on; medians of the two servers).

| configuration | prefill t/s | decode t/s | ms / step | draft accepted |
|---|---|---|---|---|
| Q5 all on | 2208 | 50.74 | 56.26 | 333 / 886 |
| **Q5 all on + 0006** | 2207 | **53.77 (+6.0%)** | **52.80 (−6.1%)** | 332 / 885 |
| MXFP4 all on | 2392 | 66.79 | 46.09 | 346 / 821 |
| MXFP4 all on + 0006 | 2389 | 67.22 | 45.79 (−0.7%) | 346 / 821 |

- Every round gave identical tokens.  Prefill is unchanged: `0006` only takes batches of 1 to 8 tokens.
- In the MXFP4 model only the output layer is a K-quant (Q6_K), so `0006` takes only that one matmul; the greedy tokens did not
  change.

## Other decode measurements

| setup | without 0006 | with 0006 (`=2`) |
|---|---|---|
| UD-Q4_K_XL, 2 slots, 245,760 context, draft 5, greedy 512 tokens, 8K / 110K prompt | 50.00 / 60.98 ms per step | 47.65 / 57.85 (−4.7% / −5.1%) |
| UD-Q4_K_XL, 1 slot, draft 5, temperature 0.7, 12 prompts × 2 seeds (Chinese, English, documentation; 4K-24K) | 49.76 ms per step, 2.301 tokens per step | paired ratio 0.942 (95% CI 0.941-0.943) per step; tokens per step 1.002 (0.961-1.046) |
| Q5_K_M (the uncensored fine-tune), 92.6K-token agent conversation (17 tools), temperature 0.3, draft 3, 20 seeds each | 55.24 ms per step | 52.74 (−4.5%) |
| Windows 10 (same GPU), 40K-token prompt, draft 3 | 51.68 ms per step | 49.83 (−3.6%) |

The draft acceptance does not change (the paired ratio above).  The agent conversation was the one where an earlier build of this
kernel was suspected of making reasoning repeat itself; with the same request, reasoning that rewrote earlier lines (20 or more in
a row) happened in 2 of 20 runs without `0006` and in 0 of 20 with it, so it is a property of that request, not of the kernel.

Forced on without a draft (`=4`, one-token decode only): Qwen3.8-27B UD-Q4_K_XL +0.6-1.1% per step, Qwen3.6-27B Q4_K_M +1.6%,
Qwen3-30B-A3B Q4_K_M −2.3%.  Hence `1` / `2` stay off without drafts.

## Quality

Long-context KLD on the decode path (48K-token prefix, then 400 teacher-forced tokens), `0006` on against off on the same build,
as a ratio to the run-to-run floor (one f16 mantissa bit of K changed):

| model | Chinese | English |
|---|---|---|
| Qwen3.8-27B Q5_K_M (an uncensored fine-tune) | 0.84× floor (top-1 99.25% vs 98.50%) | 0.52× (98.75% vs 99.50%) |
| Qwen3.6-27B Q4_K_M | 0.86× (97.50% vs 98.50%) | 0.58× (98.50% vs 98.50%) |

A German-to-Chinese translation of a paragraph 35K tokens back gave the same content; in one greedy run the Chinese switched from
Traditional to Simplified script halfway, which lowers chrF (0.56) without changing what the sentences say.

Models whose weights `0006` does not take (Mistral-7B Q8_0, phi-4 IQ4_XS) give identical tokens and speed with it on.

## Reliability

UD-Q4_K_XL and Qwen3.6-35B-A3B with their DFlash drafts, 4 slots, 16 kinds of request (tool-calling chats, reasoning at
temperature 0.7, short chats, long text continuation), 2 one-at-a-time rounds, 3 concurrent rounds and 4 copies of one request at
once: no errors, no crashes, no runaway output, valid tool-call JSON, the one-at-a-time rounds repeat exactly, and the concurrent
rounds differ from them as often as without `0006`.  Two prompts prefilled in one batch differ from each prompt alone only at
near ties (the 2nd-4th candidate, from token 8 on), as without `0006`.

# 基準測試 2026-10-18

本文件由 Claude（AI）撰寫。patch 組合：同 [2026-10-15](2026-10-15.md) 的 `0001`～`0005`，加上新的 `0006-097-mmvk-v2`，基底 rdna-boosts `v12-097cf33d9-r59`。未註明時皆為 R9700、Linux。

## 0006 是什麼

decode 與推測解碼的驗證，矩陣乘一次只有 1～8 個 token。`0006` 讓 Q4_K／Q5_K／Q6_K 權重在這裡改用另一個 kernel：每個 lane 負責 32 個值的一段，把所有 token 的 q8_1 activation 只載入一次，給多列權重重複使用；`GGML_CUDA_MMVK=2` 時，讀同一個輸入的矩陣乘（gate＋up、q＋k＋v、DeltaNet qkv＋z）也合併成一次發射，不同權重型別可以混在一起。

- 整數內積與縮放和原版 kernel 相同，只有浮點加總的順序不同，所以和原版不逐位元相同。decode 與驗證用同一個加總順序，所以帶草稿和不帶草稿的輸出逐 token 相同。
- `1`／`2` 只在 llama-server 驗證草稿時開（草稿模型、MTP 或 ngram）：llama-server 載入模型前會通知後端，log 印出 `mmvk on (...)` 或 `mmvk off (...)`。沒有草稿時每一步都是單 token decode，這時原版 kernel 在 27B 模型上反而快 1～1.6%（見下）。`3`／`4` 強制開。
- 不設 `GGML_CUDA_MMVK` 就不作用。它不接手的權重型別（Q8_0、IQ4_XS、MXFP4 等）完全不受影響。

## 標準基準

設定同 [2026-10-07](2026-10-07.md)（32K token prompt、greedy 512 token、DFlash2 草稿 5、q8_0 KV、3 輪），「全開」同 2026-10-15。兩種設定在同一時段跑（Q5：全開、＋0006、＋0006、全開；取兩個 server 的中位數）。

| 設定 | prefill t/s | decode t/s | 每步 ms | 草稿接受 |
|---|---|---|---|---|
| Q5 全開 | 2208 | 50.74 | 56.26 | 333 / 886 |
| **Q5 全開＋0006** | 2207 | **53.77（+6.0%）** | **52.80（−6.1%）** | 332 / 885 |
| MXFP4 全開 | 2392 | 66.79 | 46.09 | 346 / 821 |
| MXFP4 全開＋0006 | 2389 | 67.22 | 45.79（−0.7%） | 346 / 821 |

- 每輪輸出逐 token 相同。prefill 不變：`0006` 只處理 1～8 token 的批次。
- MXFP4 模型裡只有輸出層是 K-quant（Q6_K），`0006` 只接手這一個矩陣乘；greedy 輸出沒有改變。

## 其他 decode 量測

| 設定 | 不加 0006 | 加 0006（`=2`） |
|---|---|---|
| UD-Q4_K_XL、2 slot、245,760 上下文、草稿 5、greedy 512 token，prompt 8K／110K | 每步 50.00／60.98 ms | 47.65／57.85（−4.7%／−5.1%） |
| UD-Q4_K_XL、1 slot、草稿 5、temperature 0.7、12 個 prompt × 2 個 seed（中文、英文、文件；4K～24K） | 每步 49.76 ms、每步 2.301 token | 成對比值：每步時間 0.942（95% CI 0.941～0.943）；每步 token 1.002（0.961～1.046） |
| Q5_K_M（去審查微調版）、92.6K token 的代理對話（17 個工具）、temperature 0.3、草稿 3、各 20 個 seed | 每步 55.24 ms | 52.74（−4.5%） |
| Windows 10（同一張卡）、40K token prompt、草稿 3 | 每步 51.68 ms | 49.83（−3.6%） |

草稿接受率不變（見上面的成對比值）。那段代理對話，就是先前懷疑這個 kernel 的早期版本會讓思考反覆重寫的那一筆；同一個請求下，思考把前面的內容連續 20 行以上照抄的情形，不加 `0006` 是 2／20，加了是 0／20，所以那是這筆請求本身的性質，不是 kernel 造成的。

沒有草稿時強制開（`=4`，只有單 token decode）：Qwen3.8-27B UD-Q4_K_XL 每步 +0.6～1.1%，Qwen3.6-27B Q4_K_M +1.6%，Qwen3-30B-A3B Q4_K_M −2.3%。所以 `1`／`2` 在沒有草稿時保持關閉。

## 品質

decode 路徑的長上下文 KLD（48K token 前文，再 teacher-force 400 個 token），同一個 build 上 `0006` 開對關，以「底噪」（K 的 f16 尾數改 1 個位元）的倍數表示：

| 模型 | 中文 | 英文 |
|---|---|---|
| Qwen3.8-27B Q5_K_M（去審查微調版） | 底噪的 0.84 倍（首選一致 99.25%，底噪 98.50%） | 0.52 倍（98.75%，99.50%） |
| Qwen3.6-27B Q4_K_M | 0.86 倍（97.50%，98.50%） | 0.58 倍（98.50%，98.50%） |

把 3.5 萬 token 之前的一段德文譯成中文，內容相同；其中一次 greedy 譯文中途由繁體轉成簡體，chrF 因此較低（0.56），但句子的意思沒有改變。

`0006` 不接手其權重的模型（Mistral-7B Q8_0、phi-4 IQ4_XS），開啟後輸出與速度都相同。

## 可靠性

UD-Q4_K_XL 與 Qwen3.6-35B-A3B（各配 DFlash 草稿）、4 slot、16 種請求（帶工具的對話、temperature 0.7 的思考、短對話、長文續寫），依序 2 輪、併發 3 輪、同一請求 4 份同時送：沒有錯誤、沒有崩潰、沒有失控輸出，工具呼叫的 JSON 都合法，依序的兩輪完全重現，併發輪和依序輪的差異次數和不加 `0006` 時相當。兩段 prompt 同批 prefill 時，和各自單獨跑只在近乎平手處不同（第 2～4 名的候選，第 8 個 token 以後），和不加 `0006` 時相同。
