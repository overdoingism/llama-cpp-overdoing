## What changed

- **A new upstream base.**  rdna-boosts moved to llama.cpp `6050b467c` at r138.  The patch code of 0001-0006 is the same as
  in the r59 set; only the context changed.  The r59 set is in `patches/r59/`.
- **On by default.**  0001-0004 and 0006 now run unless their switch is set to `0`; `GGML_LF_ALL=0` turns off every switch
  left unset (the build then gives the same output as plain r144: checked below, KLD 0).  K1's default is fp8, and only
  where every GPU is a gfx1201 (its built-in algorithm lists were measured there).  See [SWITCHES.md](../SWITCHES.md).
- **0007 is now the lenience.**  llama.cpp now samples DFlash2 drafts itself (`--spec-draft-sampling probabilistic`), which
  is what the old 0007 added.  The new 0007 adds a lenience to that verification (below); it is lossy and off by default.
- **0008** fixes the Windows build of r143 and later (rdna-boosts issue #231); nothing changes on Linux.
- **0009** is new: draft-verification batches of 9-16 rows through the decode / verify attention kernel (below).

## 0007: lenience for sampled drafts

With sampled drafts, llama.cpp accepts a drafted token x with probability min(1, p(x) / q(x)) (p: the model, q: the draft),
and on a rejection draws from norm(max(0, p − q)); the output then follows the model's distribution exactly.  0007 accepts
with min(1, p(x) / (l·q(x))) for a lenience l < 1 and keeps the rest: more drafted tokens are kept, the output distribution
changes, and no token becomes more than 1/l times as likely as under the model (the "lenience" of Leviathan et al., 2023).
`LLAMA_SPEC_LENIENCE=<l>` sets it for every request, the request field `spec_lenience` per request; unset, or at
temperature 0, nothing changes.  At l = 1 the build gives the same tokens as llama.cpp's own verification, seed for seed
(2000 of 2000 in the distribution check; llama.cpp's sampled DFlash2 drafting itself showed no bias, 0 of 36 tests below
p = 0.05).

Quality, on Qwen3.8-27B with thinking on (measured on an earlier base with the same verification code):

- **l = 0.5 is too lenient**: in 10 recorded agent turns at temperature 1, one ended in a loop of about 16,000 tokens
  that repeated itself word for word.  Once text starts to repeat, the draft and the model both favor going on, and the
  lenience raises the acceptance exactly there.
- **l = 0.85**: no loop in the same 10 turns.  The length of the reasoning spread out more than in the exact runs (5 turns
  shorter than every exact sample, 2 longer; not significant with 10 turns).
- **l = 0.8663**, a tool-calling task bank (two runs per case, temperature 1): 93 of 104 passed against 91 of 102 at
  l = 1, the same number of cases passed twice (43 of 52).  This can only rule out a large drop (about 10 points).

Speed on r144, production setup (UD-Q4_K_XL, DFlash2 draft of 5, 2 slots, `-c 245760`), two rounds with different seeds,
tokens/s against greedy drafting:

| requests | sampled drafts | + lenience 0.8663 |
|---|---|---|
| recorded agent turns as sent (temperature 0.3, top-p 0.9) | +2.4% | +4.8% |
| the same turns at temperature 1.0 / top-p 0.95 / top-k 20 | +12.1% | +20.3% |
| code at temperature 0.7, no thinking | −0.4% | −0.9% |
| tool-calling turns at temperature 0 | same text, ±0.2% | same text, ±0.2% |

So on r144 sampled drafts no longer cost speed at 0.3 (on r115 they did, −3.5%), and the lenience adds 2-8 points on top.
Measure on your own workload and judge the quality yourself: 0007 is lossy by design.

## 0009: verify batches of 9-16 rows

On RDNA4, rdna-boosts runs attention for 1-8 query rows (decode and draft verification) through a "band" kernel that reads
each K/V element once per query group; wider batches fall back to the generic WMMA kernel, which for Qwen3.8-27B (GQA 6)
reads every K/V element three times.  Batches of 9-16 rows are common with `--parallel 2` and a unified KV cache: two slots
that verify drafts of the same width share one ubatch (2 × 6 rows with a DFlash2 draft of 5), and an n-gram draft longer
than 7 makes one by itself.  Attention rows are independent, so 0009 runs such a batch as two halves of at most 8 rows
through the band; each row gets the result a batch of 8 rows or fewer gives.

Measured on rdna-boosts r123 with the same code (Qwen3.8-27B UD-Q4_K_XL, production setup, q8_0 KV):

| | 8K cells | 110K cells |
|---|---|---|
| one verify step, 12 / 16 rows (one sequence) | −1.9 / −2.2% | **−33.7 / −33.2%** (106.8 → 70.7 ms, 109.3 → 73.0 ms) |
| one verify step, 6 + 6 / 8 + 8 rows (two slots) | −2.4 / −2.5% | **−30.8 / −30.1%** |

| two slots decoding at once, tokens/s of the pair against the two run one after the other | 8K each | 50K each |
|---|---|---|
| without 0009 | +25 / +34% | **−13 / −19%** |
| with 0009 | +40 / +42% | **+38 / +33%** |

Below 8192 KV cells the two launches cost more than the one they replace (+0.4 to +2.5% per step at 1K-4K), so 0009 splits
only from there (`GGML_CUDA_FA_BAND_SPLIT_MIN_KV`).  Batches of 8 rows or fewer, and two slots verifying different widths
(those are already two ubatches), do not change.  `test-backend-ops`: the band shape at 9 / 12 / 16 rows (f16 / bf16 / q8_0
KV, 512 / 4096 / 16384 cells, three mask forms) against the CPU: 108 of 108 on r123 with the split on and off; on r144,
109 of 109 with the default (split from 8192 cells), with `GGML_CUDA_FA_BAND_SPLIT_MIN_KV=0` (every case splits) and with the
split off.  The KLD run and the
standard benchmark above have no batches of 9-16 rows, so 0009 changes neither.

## 0002 v5: the row sum of F8

F8 runs the prefill attention in fp8: P = exp2(s - max + 8) (scaled by 2^8 into the fp8 range) is converted to fp8 for
the P·V WMMA, but v4 added the fp32 values of P into the row sum l.  A probability below the smallest fp8 subnormal
(about 2^-18 of the row's running maximum) became 0 in the numerator but stayed in the denominator, a bias toward a
smaller output that grows with the number of small weights, that is, with the context.  v5 converts the eight fp8
values back to fp32 and adds those, so numerator and denominator use the same numbers (the principle of Barron et al.,
"A Fix for Softmax and Cross-Entropy", arXiv 2610.31642, written for training; nothing upstream has an fp8 attention
path).

KLD against plain r144 (Qwen3.8-27B Q5_K_M (JonathanColetti's Uncensored, the model of an earlier long-context check),
a chat-formatted conversation with reasoning blocks, then a held-out reasoning block and answer teacher-forced; ub
2048; the floor, one bit of K changed, from that earlier check: 60K 0.00023, 165K 0.00021):

| | 60K | 170K |
|---|---|---|
| F8 alone, v4 | 0.000247 | 0.000396 |
| F8 alone, v5 | 0.000285 | **0.000307** |
| all defaults (K1 fp8 + F8), v4 | 0.000488 | 0.000621 |
| all defaults, v5 | 0.000421 | 0.000618 |

At 170K F8's own error drops by a fifth; at 60K both are at the floor (any one-bit change gives about 0.0002 on this
model).  With all defaults K1 fp8's error dominates, and the change stays below the floor.  The top-1 token agrees on
99.1-99.6% of the positions in every case.  Prefill speed (R9700, Windows, XL, 1 slot, no draft, servers alternated):
32K 2376.6 → 2384.5 tokens/s, 110K 1934.2 → 1939.8 (+0.3%).

## 0012, 0014, 0015: draft length

Production setup throughout (Qwen3.8-27B UD-Q4_K_XL, DFlash2 Q4_K_M draft of 5, `--parallel 2 --kv-unified`, `-c 245760`,
sampled drafts with the lenience of 0007, greedy requests).

**0012, DFlash2 adaptive verify width.**  Each sequence drafts the width with the most tokens per unit of step cost,
from running per-position acceptance estimates.  One request at a time (earlier base, same code): general workloads
+0.1 % (novel +1.4 %, code and tool calls within ±0.2 %), low-acceptance long Chinese text +5..+11 %; the output does
not change.  Two slots decoding at once, a low-acceptance zh text next to an en text:

| two slots at once, pair tokens/s against fixed width 5 | 8K each | 50K each |
|---|---|---|
| 0012 without 0015 | **−15.6 %** | **−23.0 %** |
| 0012 with 0015 | +0.1 % | −6 % (within noise: fixed width gave 85.8 and 98.7 in two runs, 0012 86.5 and 86.5) |

The zh slot ran at width 2-3 and the en slot at 5; Qwen3.8 is a hybrid model, and llama.cpp splits a batch whose
sequences differ in length into ubatches of equal length, so every step ran the weights twice.

**0014, shadow n-gram.**  With `--spec-type ngram-mod,draft-dflash` the n-gram drafts wait until they have predicted 24
of the model's tokens in a row, then replace DFlash2 until one misses.  One request at a time: all +10.6 %, whole-file
rewrites +38..+68 %, opencode turns and tool calls within ±1 % (24 is the lowest threshold with no request group slower;
12 took two tool-call answers for copying, −28..−30 %).  With `LLAMA_SPEC_NGRAM_SHADOW_EXACT=1` the output equals
DFlash2 alone (6 of 6 on Qwen3.8-27B, 6 of 6 on Qwen3.6-35B-A3B) and rewrites gain about half as much.  No errors with 2
and 4 slots under mixed concurrent load, nor on Qwen3.6-35B-A3B.

**0015, one draft length per verify batch.**  A file rewrite (copying, 16-row drafts) and an 8K zh continuation at once:

| tokens/s while both emit | DFlash2 alone | 0014 without 0015 | 0014 with 0015 | 0012 + 0014 + 0015 |
|---|---|---|---|---|
| copying slot | 68.2 | 89.8 (+32 %) | 89.1 (+31 %) | 90.0 (+32 %) |
| zh slot | 20.7 | **10.9 (−47 %)** | 20.7 (−0.2 %) | 20.9 (+0.9 %) |
| pair | 88.9 | 100.7 (+13 %) | 109.8 (+23 %) | 110.9 (+25 %) |

(The "0014 without 0015" column is from a separate run whose DFlash2-alone figures were 68.0 / 20.7 / 88.7; percentages
against those.)

0015 aligns DFlash2's adaptive width up to the longest draft of the batch (up to `--spec-draft-n-max`) and cuts a
longer draft (a copying n-gram draft) to the shortest; it acts only on hybrid / recurrent models.
