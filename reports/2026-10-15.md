# Benchmark 2026-10-15

Patch set: `0001-097-k1-v3.2`, `0002-097-f8-v3.3`, `0003-097-m4-v2`, `0004-097-reasoning-guard-v1` on rdna-boosts
`v12-097cf33d9-r59`; `0005-097-backend-sampling-reserve-v1` was added later the same day (last section).  Written with Claude (AI).  Same setup as [2026-10-07](2026-10-07.md) (standard benchmark: 32K-token prompt,
512 greedy tokens, DFlash2 draft 5, q8_0 KV, 3 rounds).

## What changed

- **r51 and later.**  rdna-boosts r51 reorganized its sources: the matmul fusions that K1 and M4 have to stand down for moved from
  `ggml-cuda.cu` to `mmq.cu`.  The patches follow; the code that runs is the same.  The r50 set stays in `patches/r50/`.
- **K1 v3.2** (`0001`): in the `fp8` mode, after a weight's first use its quant blocks go to fp8 in one kernel instead of through
  an f16 copy.  The bytes are the same as before, so the output is the same as v3.
- **Reasoning guard** (`0004`, new, `LLAMA_REASONING_GUARD=1`): see below.

## Standard benchmark

| configuration | prefill t/s | decode t/s | ms / step | draft accepted |
|---|---|---|---|---|
| Q5 all off (plain r59) | 1125 | 51.11 | 56.17 | 334 / 876 |
| **Q5 all on** | **2197 (+95%)** | 50.42 | 56.62 | 333 / 886 |
| MXFP4 all off (plain r59) | 1335 | 60.00 | 46.79 | 330 / 899 |
| **MXFP4 all on** | **2365 (+77%)** | **66.23 (+10%)** | 46.48 | 346 / 821 |

- Every round gave identical tokens.  Run-to-run CV: prefill 0.1-1.4%, decode 0.7-1.2%.
- The tokens and draft counts equal r50's (2026-10-13), plain and all on.  Q5 all on goes from 1959 (K1 v3 on r50) to 2197 t/s:
  that is K1 v3.2.
- With every switch off, the patched build gives exactly plain r59's tokens (UD-Q4_K_XL, three tool-calling chats).

## Same output as r50

Against the r50 build with the same patches: a 48,000-token Chinese and English prefix, then 400 greedy tokens, all on.  The
tokens and the top-10 log-probabilities of every position are identical.  The quality check of [2026-10-13](2026-10-13.md)
therefore holds for r59 as well (zh 1.29x, en 1.38x the numerical floor).

## Reasoning guard

A reasoning model can end its turn while still inside the reasoning block: the answer is written there, and the reply is empty.
We saw it with agentic coding clients that send earlier reasoning back as plain text, over long contexts.  It also happens on
plain builds (plain rdna-boosts r50: 1 of 3 seeds on such a request; plain r59 with Qwen3.6-35B-A3B: 1 of 72 replies in a
mixed load).

With `LLAMA_REASONING_GUARD=1`, an end of turn sampled inside the reasoning block is replaced by the block's end tag, and
generation goes on.  Everything before that point is sampled as usual, so the reasoning is never shortened; a reply cut by
`max_tokens` stays as it is.

- **When it does not fire, nothing changes.**  The production setup (UD-Q4_K_XL, 2 slots, all on) gives the same three chats
  with and without it.
- **When it fires, the answer is rescued.**  A real 72,500-token multi-turn request, 1 slot, temperature 0.3 (on the r50 build;
  the guard code and the outputs are the same on r59): two seeds that
  had ended with an empty reply now produced their answer after the reasoning.  The model wrote out the answer it had put in the
  reasoning (similarity 0.994 and 1.000), at a cost of 2,600 and 4,900 extra tokens; one of them went past the request's
  `max_tokens` of 25,000.  Leave room in `max_tokens`.
- A line in the system prompt does not do this.  At the token where the failing runs started the answer inside the reasoning,
  the probability of the end tag was 0.01-0.1%; the best of five wordings raised it to 0.05-1.3%.

## Backend sampling fix (0005)

With `--backend-sampling`, llama.cpp asks for a reserve every time a backend sampler is set or removed.  The server sets a new
sampler chain for every request, and removes it for a grammar request (backend sampling turns itself off there).  A reserve
creates a new scheduler, so all compute buffers were freed and allocated again, at the same size, before the first token.
This is upstream llama.cpp code: master `23deec025` does the same.  `0005` asks for a reserve only when the buffers were not
reserved with a backend sampler for that sequence.  A chain set again or removed needs none: the graph is rebuilt anyway, and
the allocator grows a buffer if a chain ever needs more.

Plain r59 against r59 + `0005`, both with `--backend-sampling`, the other switches off, 1 slot, `-c 16384`, 8 identical
requests (64-token prompt, 32 tokens, temperature 0.8, seed 42):

| model, ubatch | freed and allocated per request, plain / 0005 | prompt time, plain / 0005 | wall time per request, plain / 0005 |
|---|---|---|---|
| Mistral-7B-Instruct-v0.3 Q8_0, `-ub 512` | 119 MiB device + 32 MiB host / 0 | 62 / 27 ms | 559 / 518 ms |
| Qwen3.8-27B UD-Q4_K_XL, `-ub 2048` | 651 MiB device + 224 MiB host / 0 | 435 / 180 ms | 1525 / 1204 ms |

- Every response (8 plain, 4 grammar and 6 alternating requests, both models) is identical with and without `0005`.
- Grammar requests, and plain and grammar requests alternating: plain r59 reserves again at every switch; with `0005` nothing is
  freed or allocated.
- 2 slots, 4 concurrent plain and grammar requests, 2 rounds: no errors; the buffers grew once, by 6.4 MiB.
- Decode speed is unchanged.  Without `--backend-sampling` the patch changes nothing.

# 2026-10-15 基準

本報告由 Claude（AI）撰寫。patch：`0001-097-k1-v3.2`、`0002-097-f8-v3.3`、`0003-097-m4-v2`、`0004-097-reasoning-guard-v1`，套在 rdna-boosts `v12-097cf33d9-r59`；`0005-097-backend-sampling-reserve-v1` 是同一天稍晚加入的（見最後一節）。條件與 [2026-10-07](2026-10-07.md) 相同（標準基準：32K token 的 prompt、greedy 生成 512 個 token、DFlash2 草稿 5、q8_0 KV、3 輪）。

## 改了什麼

- **支援 r51 以後**：rdna-boosts 在 r51 重新整理了原始碼，K1、M4 需要退讓的矩陣乘融合從 `ggml-cuda.cu` 搬到了 `mmq.cu`。patch 跟著移過去，實際執行的程式碼不變。r50 版留在 `patches/r50/`。
- **K1 v3.2**（`0001`）：`fp8` 模式下，權重第一次用過之後，直接從量化區塊一步轉成 fp8，不再經過 f16 複本。產生的位元組和之前相同，所以輸出和 v3 相同。
- **思考區守門**（`0004`，新增，`LLAMA_REASONING_GUARD=1`）：見下文。

## 標準基準

| 設定 | prefill t/s | decode t/s | 每步 ms | 草稿接受 |
|---|---|---|---|---|
| Q5 全關（原版 r59） | 1125 | 51.11 | 56.17 | 334 / 876 |
| **Q5 全開** | **2197（+95%）** | 50.42 | 56.62 | 333 / 886 |
| MXFP4 全關（原版 r59） | 1335 | 60.00 | 46.79 | 330 / 899 |
| **MXFP4 全開** | **2365（+77%）** | **66.23（+10%）** | 46.48 | 346 / 821 |

- 全開＝`GGML_LF_KQ_BLAS=fp8`（KEEP 64）、`GGML_LF_FA_FP8=1`、`GGML_LF_MXFP4_DIRECT=blaslt`、`GGML_LF_DRAFT_UB=512`。
- 每一輪的 token 都相同。輪間變異：prefill 0.1～1.4%，decode 0.7～1.2%。
- token 與草稿接受數和 r50（2026-10-13）相同，原版與全開都是。Q5 全開從 1959（r50 上的 K1 v3）到 2197 t/s，這是 K1 v3.2 的效果。
- 所有開關關閉時，套了 patch 的 build 和原版 r59 的 token 完全相同（UD-Q4_K_XL、三段帶工具呼叫的對話）。

## 和 r50 的輸出相同

和套同一組 patch 的 r50 build 比：48,000 token 的中文、英文前綴，接著 greedy 生成 400 個 token，全開。token 與每個位置的前 10 名 log-prob 完全相同，所以 [2026-10-13](2026-10-13.md) 的品質檢查在 r59 上同樣成立（中文 1.29 倍、英文 1.38 倍底噪）。

## 思考區守門

推理模型有時會在思考區裡直接結束回合：答案寫在思考區，正文是空的。我們在把舊的思考內容當一般文字送回的程式代理類前端、長上下文的情況下遇到。原版也會發生（原版 rdna-boosts r50：這類請求 3 個 seed 中 1 個；原版 r59 配 Qwen3.6-35B-A3B：混合負載 72 個回覆中 1 個）。

設定 `LLAMA_REASONING_GUARD=1` 時，在思考區裡抽到「結束回合」會被換成思考區的結束標籤，然後繼續生成。在那之前的每個 token 都照常抽樣，所以思考不會被縮短；被 `max_tokens` 截斷的回覆也照舊。

- **沒觸發時完全不變**：正職設定（UD-Q4_K_XL、2 slot、全開）開與不開，三段對話的輸出相同。
- **觸發時能救回答案**：一筆真實的 72,500 token 多輪請求、1 slot、temperature 0.3（在 r50 build 上量；守門程式碼與輸出在 r59 上相同）。原本以空正文結束的兩個 seed，現在都在思考之後寫出了答案：模型把它在思考區寫好的答案再寫一次（相似度 0.994 與 1.000），多花 2,600 和 4,900 個 token，其中一個超過該請求 25,000 的 `max_tokens`。`max_tokens` 請留餘裕。
- 在系統提示加一句話做不到這件事：在失敗的那幾次開始把答案寫進思考區的那個位置，結束標籤的機率是 0.01～0.1%；五種寫法中最好的一種只拉到 0.05～1.3%。

## backend sampling 修正（0005）

開 `--backend-sampling` 時，llama.cpp 每次掛上或拿掉 backend 取樣器都會要求重新規劃計算圖。伺服器每個請求都會掛上一條新的取樣鏈，遇到 grammar 請求又會把它拿掉（backend 取樣在那裡會自動關閉）。重新規劃會建立新的排程器，所以在第一個 token 出來之前，全部計算緩衝區都要先釋放、再以同樣大小重新配置。這是上游 llama.cpp 的程式碼，master `23deec025` 也一樣。`0005` 只在這個序列的緩衝區還沒以 backend 取樣器規劃過時才要求重新規劃；換一條取樣鏈或拿掉時都不需要，因為圖本來就會重建，緩衝區萬一不夠，配置器也會自己放大。

原版 r59 對 r59＋`0005`，兩邊都開 `--backend-sampling`、其他開關全關，1 slot、`-c 16384`，8 個相同的請求（64 token 的 prompt、生成 32 個 token、temperature 0.8、seed 42）：

| 模型、ubatch | 每個請求釋放並重新配置（原版／0005） | prompt 時間（原版／0005） | 每個請求總時間（原版／0005） |
|---|---|---|---|
| Mistral-7B-Instruct-v0.3 Q8_0、`-ub 512` | 顯存 119 MiB＋主機 32 MiB／0 | 62／27 ms | 559／518 ms |
| Qwen3.8-27B UD-Q4_K_XL、`-ub 2048` | 顯存 651 MiB＋主機 224 MiB／0 | 435／180 ms | 1525／1204 ms |

- 所有回覆（兩個模型，各 8 個一般、4 個 grammar、6 個交替的請求）開不開 `0005` 都逐字相同。
- grammar 請求，以及一般和 grammar 請求交替：原版每次切換都重新規劃；`0005` 完全沒有釋放或配置。
- 2 slot、一般和 grammar 混合 4 個請求同時送，跑 2 輪：沒有錯誤；緩衝區只放大過一次，6.4 MiB。
- decode 速度不變。不開 `--backend-sampling` 時，這個 patch 不改變任何東西。
